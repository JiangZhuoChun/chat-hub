# W8-9 最终送达回执需求文档

> **W9 协议修订（2026-08-13）**：本文件最初的 W8 版本以 `{ recipient_username, local_id }` 关联回执；SQLite 引入服务端全局
`message_id` 后，以下旧合同整体由本修订替代。B → Server 的回执为 `{ "message_id": "..." }`，`PendingDeliveryMap` 为
`message_id -> { sender_username, sender_session_id, sender_local_id, recipient_username }`。服务端必须用认证身份确认回执者正是保存的
`recipient_username`，再向 A 发送 `{ "local_id": sender_local_id, "status": "delivered" }`。A 的 UI 仍只通过 `local_id`
> 更新既有气泡。旧段落保留用于说明 W8 的演进背景，不得作为当前实现依据。

## 1. 目标

在现有 `chat_ack`（服务器已接受）的基础上，增加 `Delivered` 状态：接收方 B 已将完整消息写入本地模型，并完成当轮聊天界面处理后，发送送达回执；服务端校验后通知原发送方
A 更新既有消息状态。

`Delivered` 表示“接收方客户端已完成本地处理”，不表示用户已阅读，也不保证物理屏幕像素已经绘制完成。

## 2. 非目标

- 不实现已读回执、跨重连补发、离线消息、数据库持久化或多端同步；
- 不修改现有 `chat`、`chat_ack`、错误帧的字段语义；
- 不为送达事件创建新聊天气泡、未读数或会话置顶；
- 不把接收方发送回执失败视为原消息发送失败。

## 3. 协议

新增帧类型 `delivery_receipt = 7`。

| 方向         | 正文                                             | 说明              |
|------------|------------------------------------------------|-----------------|
| B → Server | `{ "local_id": "..." }`                        | B 回执已处理的原消息     |
| Server → A | `{ "local_id": "...", "status": "delivered" }` | 服务端校验通过后的最终送达通知 |

`local_id` 必须是非空字符串，最大长度沿用聊天 `local_id` 的 64 字节限制。未知、重复或不属于当前认证用户的回执均拒绝，且不得更新
A 的状态。

## 4. 服务端数据与生命周期

服务端维护仅驻留内存的待送达记录：

```text
键：{ recipient_username, local_id }
值：{ sender_username, sender_session_id }
```

1. A 的 `chat` 通过现有校验并成功转发给 B 后，登记待送达记录；
2. B 的 `delivery_receipt` 到达后，服务端从认证会话得到 B 的用户名，用 `{B, local_id}` 查找并校验；
3. 校验通过时，向 A 转发 `status=delivered`，随后删除记录；
4. 重复、未知或冒充回执安全拒绝；
5. A 或 B 断开时，清理关联记录。A 的气泡保持 `Accepted`，不跨重连补发。

## 5. 客户端与 UI 边界

| 模块                  | 新增 API / 状态                                            | 职责                            |
|---------------------|--------------------------------------------------------|-------------------------------|
| `ChatMessageStatus` | `Delivered`                                            | 表示原发送消息已最终送达                  |
| `ChatClient`        | `sendDeliveryReceipt(local_id)`                        | 仅编码并发送 B 的回执                  |
| `ChatClient`        | `handleDeliveryReceiptBody()` + `chatMessageDelivered` | 解析 A 收到的最终状态更新                |
| `MainWindow`        | `onChatMessageDelivered(update)`                       | 按 `local_id` 更新已有消息，绝不新增气泡或排序 |
| 气泡渲染                | `Delivered` 显示“已送达”                                    | 仅作用于本人发送的消息                   |

B 的 `onChatMessageReceived()` 必须在写入模型、会话项处理与当前界面渲染或列表刷新完成后，才请求发送回执。非当前会话虽不渲染右侧气泡，但已写入模型并刷新会话列表，仍可回执。

## 6. 分块编码顺序

### 步骤 1：协议常量与客户端骨架

**涉及文件：** `chat_protocol.h`、`chat_types.h`、`chatclient.h/.cpp`。

1. 在 `MessageType` 中新增 `delivery_receipt = 7`，并把 `isKnownMessageType()` 的上界同步扩展到该类型；否则帧会在解码阶段被当成未知类型丢弃。
2. 在 `ChatMessageStatus` 中新增 `Delivered`。它表示“接收方已经完成本地处理”，与服务器已接受的 `Accepted` 分开。
3. 为 `ChatClient` 声明 `sendDeliveryReceipt(local_id)`、`handleDeliveryReceiptBody()` 和 `chatMessageDelivered(update)`
   ：前者只负责编码 B 的回执，后两者只负责解析 A 收到的最终状态通知并转交 UI。
4. `sendDeliveryReceipt()` 先去除 `local_id` 首尾空白并检查认证状态，再用紧凑 JSON 编码 `{ "local_id": "..." }`，最后通过现有
   `writeFrame()` 发送 type=7 帧。发送失败只报告 `serverError`，不能把 A 的原消息改为失败。
5. 在客户端入站分派中为 type=7 调用 `handleDeliveryReceiptBody()`。解析时先验证 JSON 对象以及 `local_id`、`status`
   都是字符串，再要求非空 ID 与 `status == "delivered"`，合格后发出携带 `Delivered` 的状态更新。

**完成边界：** 本步骤不改会话模型和界面；客户端只具备“能发回执、能识别通知”的协议能力。

### 步骤 2：服务端路由、待送达记录与清理

**涉及文件：** `server.h/.cpp`、`session.cpp`、`chat_payload.h/.cpp`、`frame_decoder_test.cpp`、服务端 `CMakeLists.txt`。

1. 在 `Server` 私有区定义 `PendingDelivery { sender_username, sender_session_id }` 和 `PendingDeliveryMap`
   ：外层键为接收者认证用户名，内层键为 `local_id`。该表只保存回执归属和发送方在线会话，不保存正文。
2. 扩展 `parseDeliveryReceiptPayload()`，拒绝非法 JSON、缺少 ID、非字符串 ID、空白 ID 和超过 64 字节的
   ID。测试目标额外编译该实现，并覆盖上述错误及正常 ID。
3. A 的 `chat` 通过既有认证、正文与在线校验后，先调用 `rememberPendingDelivery(B, local_id, A, A_session)`；`emplace()`
   失败说明同一 B 下出现重复 ID，返回 `duplicate_local_id`，不覆盖原记录、也不转发消息。
4. `Session` 只把已认证状态下的 `chat` 与 `delivery_receipt` 交给 `Server`；`Server::onSessionMessage()`
   再按类型分派，避免把不属于聊天服务端的类型误走私聊路由。
5. B 的回执到达 `handleDeliveryReceipt()` 后，服务端从 `receipt_sender_id -> m_session_to_username` 得到真实 B，使用两次
   `find()` 查 `pending[B][local_id]`。未知、重复或 C 冒充 B 的回执没有对应记录，只向该回执发送者返回错误，绝不通知 A。
6. 查找成功后，服务端向登记时保存的 A 会话发送 `{ "local_id": "...", "status": "delivered" }`
   ，然后删除这一条待送达记录；同一回执第二次到达自然变为未知回执。
7. `removeSession()` 在删除认证映射前保存断开用户名，再清理两类记录：B 断开删除 `pending[B]`；A 断开遍历所有内层表，删除
   `sender_session_id == disconnected_session_id` 的条目。迭代删除必须写成 `it = erase(it)`，不能在已失效的迭代器上继续
   `++it`。

**完成边界：** 服务端以认证身份确定回执归属；不信任回执正文中的任何发送者/接收者信息，也不做持久化或重连补发。

### 步骤 3：接收方 B 在本地处理后发送回执

**涉及文件：** `mainwindow.cpp`。

1. `onChatMessageReceived()` 先把 `ChatMessage` 写入 `m_conversations[message.from]`，确保会话项存在并置顶。
2. 当前会话渲染右侧消息；非当前会话只增加未读数。两种分支都会刷新会话项，表示消息已经进入本地模型和本轮 UI 处理已完成。
3. 只在这些操作之后调用 `m_chat->sendDeliveryReceipt(message.local_id)`。因此 `Delivered` 不表示网络包刚抵达，而表示 B
   已完成本功能定义的本地接收处理。

**完成边界：** 回执不创建额外聊天消息，也不影响 B 的未读数和会话排序；回执发送失败只提示 B，不回滚已收到的消息。

### 步骤 4：发送方 A 更新既有消息与气泡显示

**涉及文件：** `mainwindow.h/.cpp`。

1. 连接 `ChatClient::chatMessageDelivered` 到 `MainWindow::onChatMessageDelivered()`。
2. 槽函数用 `findMessageByLocalId()` 查找已有消息；找不到时仅提示“收到未知送达回执”，不能因状态帧补建消息、会话项或未读数。
3. 找到消息后只更新它的 `status` 和错误原因；仅当这条消息所属会话正处于当前页时重新渲染。这里不调用
   `moveConversationItemToTop()`，因为状态变更不是新消息写入。
4. `appendMessageBubble()` 对“当前用户名发送且状态为 `Delivered`”的气泡追加独立一行 `已送达`。时间文本改为调用已有的
   `formatConversationTime(send_at, now)`：该函数负责今天/昨天/同年/跨年的相对格式；气泡已经持有具体消息，不能硬编码绝对日期绕过该规则。

**完成边界：** A 只更新自己的原消息；B 不会因为回执而收到新气泡或“已送达”标签。

### 步骤 5：构建、回归与人工验收

1. 每个代码块完成后执行 `cmake --build build`；协议解析变更同时执行 `ctest --test-dir build --output-on-failure`，确认
   `frame_decoder_test` 和现有 `jwt_demo` 均通过。
2. 双客户端正常路径：A 发给 B 后，A 先显示 `Accepted`；B 的消息写入模型并完成界面处理后，A 的同一气泡显示“已送达”。
3. UI 回归：B 只收到一条聊天消息；A 的送达状态不新建气泡、不修改未读数、不改变会话列表顺序；切换会话后状态仍从模型正确渲染。
4. 防御性路径的预期：非法/未知/重复回执只收到错误；C 即使猜中 `local_id` 也不能更新 A；A 或 B 断开后关联内存记录会清理，A 维持
   `Accepted`。

**本次已验证：** 正常双客户端送达、构建成功及 CTest 2/2 通过。其余防御性路径已在实现中明确限定，后续若单独做协议注入测试，应以本节预期为验收标准。

## 7. 最终验收

- A → B：A 先看到 `Accepted`，B 完成本地处理后 A 变为“已送达”；
- B 不发送有效回执、断线或服务端拒绝回执时，A 不得误变为 `Delivered`；
- C 不能借任意 `local_id` 让 A 的消息变为已送达；
- 重复回执不重复更新、不创建气泡、不改变会话顺序；
- 构建通过、CTest 通过，已有私聊、失败重试、未读数和会话排序不回退。
