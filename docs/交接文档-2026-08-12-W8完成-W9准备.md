## 4. 当前架构必须保持的规则

```text
Qt MainWindow
  └─ m_conversations：完整 ChatMessage 的唯一数据源
       └─ 状态更新只按 local_id 找到已有消息并修改状态

Qt ChatClient
  └─ QTcpSocket：协议编解码、认证状态、在线快照缓存；不直接操作 QListWidget

Asio Server（m_strand）
  ├─ m_sessions：全部 TCP 会话，含未认证连接
  ├─ username <-> SessionId：仅认证用户的双向在线路由表
  └─ m_pendingDeliveries：W8 临时内存回执索引，不保存正文、不跨重连
```

- `m_sessions` 不能用于推导在线用户名，因为它包含尚未认证的 TCP 会话。
- 在线状态是**完整快照替换**，不是客户端自己推断的上线/下线增量。
- `PendingDeliveryMap` 的键是 `{recipient_username, local_id}`；回执归属必须由认证会话确定，不能信任正文中的身份字段。
- 当前 `Delivered` 不是已读回执，也不承诺跨断线、多端或同名顶替后的送达通知。
- Qt 客户端固定使用 `QNetworkAccessManager + QTcpSocket`，服务端使用 standalone Asio；不要为 V1 引入第二套客户端网络栈。

## 5. 本次只读审查的待决建议

这些是改进建议，不是已实现功能。开始任何代码前，应先按大型项目四阶段流程确认目标与取舍。

### P1：优先在 W9 设计中处理

1. **统一消息容量契约**：当前整个 frame body 上限为 1024B，而 `content` 本身也允许 1024B；JSON 封装后接近上限的消息必然发送失败。明确“1024B
   是 body 总上限还是纯文本上限”，并把两端限制收敛到同一协议常量，补边界测试。
2. **持久消息绑定账号而非 SessionId**：当前最终送达索引保存 `sender_session_id`。同名登录顶替/断线时，旧会话的待送达记录会清理，不能向新会话迁移。W9
   应引入持久 `message_id`，用发送者/接收者账号建立消息归属。
3. **待送达记录的过期与容量策略**：接收者保持在线却不发送回执时，内存表没有 TTL 或数量上限。W9 的持久模型应有创建时间、过期策略和适当索引。
4. **在线快照容量策略**：名单 JSON 超过协议 body 上限时，当前服务端不发送新快照，客户端会保留旧名单。W9/W10
   前需确定人数上限，或设计分页/分片快照。

### P1：稳定性与验收

5. **认证阶段超时**：TCP 建连后若服务端不返回认证帧，客户端会停在 `waitingAuthResult`；服务端的未认证连接也可长期占用
   Socket。应分别设计客户端认证计时器与服务端认证期限。
6. **路由自动化测试**：现有 CTest 只覆盖帧解码与 JWT。W9 前应至少覆盖：私聊 ack、送达回执、同名顶替、断线清理、在线快照超长。

### 当前不建议为消警而改动

`HttpClient` 已通过“父对象 `QTimer` + `reply->abort()`”实现应用层超时。不要仅因为静态检查提示再叠加
`QNetworkRequest::setTransferTimeout()`；若要调整，应先统一两者的超时语义。

## 7. W14 后的架构演进预案（不属于当前主线）

**触发条件：** 只有 W9–W14 全部验收、单机版本可由陌生人按 README 复现后，才允许启动“多服务扩展
spike”。它是独立实验，不得回头破坏已经可交付的单机版本。

当前 ChatHub 是“模块化单机全栈”：独立 Auth Service + 单个 Asio ChatServer；ChatServer 内部通过 `strand`、Session、路由和
Repository 分层。未来演进目标是“可横向扩展的服务化架构”，而不是为了服务数量而拆分：

```text
Qt Client → Gateway / 接入层
              ├─ Auth / User（账户、JWT、关系）
              ├─ Chat Access Server × N（TCP Session、本机收发）
              ├─ SessionRegistry（用户 → 所在实例）
              └─ Message / Relation Repository → MySQL
                         └─ Redis（在线路由与受控短期状态）
```

演进顺序必须是：

1. 先抽象 `SessionRegistry`：单机实现仍使用内存；多节点实现才改为 Redis。`SessionId` 仍只是某个连接的短期身份，不进入消息归属。
2. 将 `sendToUser()` 拆成“目标在本机则投递 / 目标在其他实例则转发 / 无有效登记则失败”三个明确结果；消息正文继续由 MySQL
   持久化，Redis 不作为消息库。
3. 最小验收只启动 **两个** ChatServer：A、B 分别连到不同实例，A 发给 B 仍可到达；其中一个实例下线时，返回可解释错误且不让另一实例崩溃。
4. 只有该 spike 的失败路径、日志、配置和测试都成立后，才评估 Gateway、RPC 或独立 Presence 服务；不得直接照搬 llfcchat 的
   Gate/Status/多 ChatServer 与全局 `Singleton` 结构。

这项预案的学习价值是能解释“单机内存映射为什么不足、拆分后新增了哪些故障点、Redis 为什么只承担在线路由/短期状态”；它不改变下一步仍从
W9 持久化需求开始的顺序。
