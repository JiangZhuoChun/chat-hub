## 2. 当前事实与问题

| 事实                                              | 证据位置                                               | 对 W10 的意义                          |
|-------------------------------------------------|----------------------------------------------------|------------------------------------|
| 单帧 JSON body 上限是 2048B；聊天 content 上限是 1024B     | chat-server/include/protocol/chat_protocol.h       | 容量必须按完整序列化 body 计算，不能只数业务字段。       |
| Auth Service 的用户名规则是 ASCII [A-Za-z0-9_]、3–20 字符 | auth-service/src/server.js                         | 可以推导最坏在线快照长度。                      |
| ChatServer 验证 JWT 后直接登记在线映射                     | chat-server/src/net/session.cpp、src/net/server.cpp | ChatServer 尚未重验用户名的容量和字符合同。        |
| 在线快照超出 2048B 时，服务端只停止广播并记录日志                    | chat-server/src/net/server.cpp                     | 服务端在线映射可能变化，客户端却保留旧快照。             |
| 客户端非法快照只报错、不清空 m_online_users                   | client-qt/chatclient.cpp                           | UI 会继续显示过期在线状态。                    |
| 客户端认证失败路径分散，旧 Socket 的断开回调可能与立即重连交错             | client-qt/chatclient.*                             | 必须先让旧连接在 idle 收尾，再通知界面，避免旧事件误伤新连接。 |
| Server Session 没有认证截止计时器                        | chat-server/include/net/session.h                  | 未认证连接可长期占用 Session。                |

必须消除的失败路径：

~~~text
新用户认证
  → Server 已改写在线映射
  → online_users 超过 2048B
  → 广播函数只记录日志并返回
  → 已登录客户端继续显示旧快照
  → 服务端与客户端的在线状态分叉
~~~

这不是普通的单次发送失败，而是完整快照合同破坏：客户端不能把旧数据继续视为当前全量状态，服务端也不能在无法发出合法快照后假装接纳新成员。

## 3. W10-1：容量与在线快照合同

### 3.1 数据所有者与不变量

| 对象     | 唯一所有者                                                          | 不变量                                |
|--------|----------------------------------------------------------------|------------------------------------|
| 认证用户名  | ChatServer 从已验证 JWT 的 username claim 得到                        | 不信任客户端正文身份；进入在线映射前重验长度和字符集。        |
| 在线成员事实 | Server strand 上的 m_username_to_session / m_session_to_username | 同一用户名最多一个当前 Session；同名接管不增加人数。     |
| 在线快照   | ChatServer 从在线映射生成                                             | 每次 online_users 都是完整集合，不能截断、不能增量。  |
| 客户端缓存  | ChatClient::m_online_users                                     | 只保存完整且通过全部校验的快照；无效快照后不能保留旧值冒充当前状态。 |

### 3.2 容量常量和上限推导

继续使用既有的 kMaxFrameBodyLength = 2048B 和 kMaxChatContentBytes = 1024B；不降低、不重定义聊天消息限制。

新增逻辑常量集中在客户端和服务端共用的协议定义中，只保留一处权威值：

| 常量                           |     值 | 用途                         |
|------------------------------|------:|----------------------------|
| kMaxFrameBodyLength          | 2048B | 所有协议帧 body 的硬上限            |
| kMaxChatContentBytes         | 1024B | chat.content 的硬上限，保持 W9 合同 |
| kMinUsernameBytes            |    3B | 认证用户名最小长度                  |
| kMaxUsernameBytes            |   20B | 认证用户名最大长度                  |
| kMaxOnlineUsersSnapshotCount |    88 | 单帧 online_users 最大不同用户名数   |

用户名仅允许 ASCII [A-Za-z0-9_]，所以字符数等于 UTF-8 字节数，且无需 JSON 转义扩张。紧凑 JSON 的最坏长度为：

~~~text
{"users":["20B 用户名", ...]}

body 字节数 = 11 + 23 × 用户数
88 人：2035B，合法
89 人：2058B，超过 2048B，非法
~~~

公式用于推导和边界测试，不替代运行时防线。实现仍必须检查实际 serialize() 后的 body 长度。

### 3.3 服务端认证准入和广播顺序

认证包含 JWT 身份验证和在线快照容量准入两个阶段，不能再理解为“JWT 可验证就立即返回 auth.ok”。

~~~text
Client → Session：auth(token)
Session：验证签名和用户名合同
Session → Server strand：请求准入(username, session_id)
Server：构造候选集合、排序、序列化、检查容量
  ├─ 合法：原子提交映射 → Session 返回 auth.ok → 广播同一完整快照
  └─ 非法：不改变映射 → 返回 error → 关闭候选连接
~~~

规则：

1. Session 验证 JWT 后进入“等待 Server 准入”状态；不得提前设置 m_authenticated、发送 auth.ok 或调用已认证回调。
2. Server 只在自己的 strand 中复制在线用户名、合并候选用户名、去重、排序、序列化和检查长度。
3. 候选用户名已在线时为同名登录接管：集合人数不增加；成功接管后旧 Session 按既有生命周期关闭。
4. 新用户名使集合超过 88 人、实际 body 超过 2048B、用户名为空、长度越界或字符非法时：两张在线映射都不改变，既有会话不被关闭或替换。
5. 准入成功后，Session 才能进入 authenticated 并入队 auth.ok；新 Session 的输出队列必须保证 auth.ok 先于该 Session 收到的
   online_users。
6. Server 向全部已认证且仍有效的会话发送同一份、预先验证过的完整快照。单个 Session 后续断开按既有路径清理，不回滚合法准入。
7. 映射、准入、同名接管和断开清理由 Server strand 串行执行；不新增 mutex、第二个在线状态所有者或 DB 线程。

### 3.4 协议与错误合同

online_users 保持 type=8，正文保持：

~~~json
{"users":["alice","bob"]}
~~~

不新增分片、页码、游标或消息 type。本期复用 type=4 error：

| 方向                  | 正文                                                                     | 触发条件                                       | 接收者行为           |
|---------------------|------------------------------------------------------------------------|--------------------------------------------|-----------------|
| Server → 候选连接       | scope=auth，code=invalid_username_claim                                 | JWT 有效但 username 缺失、为空、非 ASCII 或长度不在 3–20B | 认证失败并断开，不入映射    |
| Server → 候选连接       | scope=online_users，code=online_snapshot_capacity_exceeded，max_users=88 | 新用户名使候选完整快照无法放入单帧                          | 认证失败并断开，不入映射    |
| Server → 已认证 Client | 完整 online_users                                                        | 快照已通过服务端所有检查                               | 严格校验后整体替换缓存和 UI |

scope 和 code 是稳定协议字段，message 只用于展示，测试不能仅断言 message。错误正文不得包含 JWT、密码、数据库路径或完整在线名单。

### 3.5 客户端快照原子替换

ChatClient::handleOnlineUsersBody() 必须遵守：

~~~text
收到 type=8
  → JSON 根对象、users 数组、元素类型、每个用户名合同、去重、人数上限全部通过
  → 临时 QStringList 完整构造成功
  → 赋值 m_online_users
  → emit onlineUsersChanged(users)

任一步失败
  → clearOnlineUsers()
  → emit serverError(明确原因)
  → 不保留旧快照，不发出“新快照成功”的信号
~~~

候选连接收到 online_snapshot_capacity_exceeded 时仍未认证：必须走认证失败路径，不能请求历史、发送聊天或显示在线名单。

### 3.6 兼容策略

- 帧头版本保持 1：没有新增 type；max_users 是可忽略的错误诊断字段。
- 旧客户端若不识别具体 code，仍必须把 type=4 当作认证失败/服务端错误，不能继续声称认证成功。
- 超过 88 人时不能截断名单或静默停止广播；第 89 个不同用户名明确被拒绝，直到人数下降。
- 将来需要大于 88 人时，必须另行设计分页/分块、快照版本或 request_id 以及客户端原子组装；W10 不扩大范围。

## 4. W10-2：认证阶段超时与三账户回归

### 4.1 可观察需求

1. TCP 建连超时与认证响应超时是两个不同阶段，两个期限均为 5000ms。
2. Server 从 Session 开始读取起启动认证截止；只有“Server 完成在线准入且确认认证成功”可以取消它。ping、任意字节、不完整帧和无效帧不能延长截止。
3. 任一侧超时后，当前连接关闭或回到 idle，清空在线快照与未完成历史请求；不得继续聊天或发送回执。
4. Server 超时向可写连接发送 scope=auth、code=authentication_timeout 的 error 后关闭；不可写时记录原因并关闭，不伪造成功。
5. Client 等待认证响应超时后发出 authFailed 并断开，不会无限显示连接中。
6. 三账户连续登录、同名接管、聊天、回执、断开重连保持 W8/W9 行为；超时连接不污染在线映射或其他账户心跳。

### 4.2 设计边界

- Server 计时器属于 Session，由 Session strand 管理；关闭、认证成功和析构都正确取消或忽略 operation_aborted。
- Client 使用独立 QTimer；writeFrame(auth) 成功并转为 waitingAuthResult 后启动；仅合法 auth.ok、断开或失败路径停止。
- 不做自动重连、指数退避或可配置的任意认证期限。

### 4.3 验收

| 场景                      | 断言                                            |
|-------------------------|-----------------------------------------------|
| TCP 未建立                 | Client 在 5 秒连接截止失败，认证计时器未启动                   |
| TCP 已建立但 Server 不回 auth | Client 约 5 秒认证失败、断开、清空快照                      |
| 原始 TCP 客户端不发认证          | Server 约 5 秒返回认证超时或记录不可写原因后关闭；在线映射不增加         |
| ping 或半包认证帧             | 不重置 Server 截止，仍按时关闭                           |
| 正常认证                    | 两侧计时取消；历史首屏和在线快照按既有顺序可用                       |
| A、B、C 连续聊天              | A→B、B→C、C→A 的 ack、Delivered、历史状态不退化；超时连接不影响三者 |

### 5.2 错误码和日志

- scope、code、message 是所有 Server error body 的公共字段；既有错误码不能重命名为含糊的 database_error。
- 本期新增错误码仅有 invalid_username_claim、online_snapshot_capacity_exceeded、authentication_timeout。
- 关键日志包含事件名、数值 Session ID、阶段、稳定错误码、实际 body 字节数或上限（适用时）。
- 不写入 JWT、密码、密钥、完整聊天正文、完整在线名单或数据库用户数据。
- 对应故障修复时，创建项目交付文档 docs/故障记录/W10-交付稳定性故障记录.md；每条记录含临时环境、触发命令、预期/实际、根因、修复、自动化覆盖和回归命令。

### 5.3 验收

- 无参数启动仍监听 9000，日志说明实际数据库路径和认证超时。
- 每个非法参数以非零退出，既不监听端口也不创建/覆盖数据库。
