# 全栈聊天软件上下文工程

本目录把通用 Context Engineering／PRP 思路改造成适用于 Windows、C++20、Qt 6、standalone Asio 和 MySQL 的中文项目工作流。它的目标是让 AI 每次只加载完成当前能力点所需的事实、合同、源码和验证信息，并通过可执行门禁形成可恢复的交付证据。

## 1. 为什么不直接复制原模板

来源模板主要面向 Python、Pydantic、FastAPI、pytest、Docker 和 Claude Code，并包含大量 MCP、Cloudflare、多代理示例。当前项目的线程所有权、TCP／TLS、MinGW、Qt 事件循环、MySQL 事务、Windows 安全和学习门禁完全不同，因此只保留以下通用思想：

- 项目级规则；
- 功能输入文件；
- 上下文充分的实施计划；
- 分层验证循环；
- 示例、决策和交接资料。

原模板中的 Python 规则、宽泛工具权限、“一条命令即可证明生产可用”和“人工测试可以完全取消”等内容没有被采用。

## 2. 目录结构


## 3. 标准流程

```text
用户提出需求／说“下一步”
        ↓
读取 AGENTS.md＋TASK.md
        ↓
用 INITIAL.md 固定目标、范围、非目标、完成条件和授权
        ↓
只读检索相关合同、源码、测试、构建和 diff
        ↓
生成 PRPs/<能力点>.md
        ↓
用户确认 PRP
        ↓
用户默认写生产代码，AI 全程教学／审查／调试
        ↓
生产接口稳定后 AI 编写测试
        ↓
自动验证＋人工验收＋解释检查
        ↓
更新 TASK、路线、项目文档、唯一学习笔记和交接
        ↓
获得 Git 授权后才暂存／提交／推送
```

## 4. 上下文最小化原则

每次任务只加载四层信息：

1. **必须常驻**：`AGENTS.md`、`TASK.md`；
2. **合同**：本步相关需求、D 决策、路线阶段和 PRP；
3. **实现证据**：直接调用链、相关测试、构建配置、日志和 diff；
4. **按需参考**：官方文档、旧工程、外部仓库和历史交接。

不要读取全部 231 条决定、整个旧仓库或所有历史记录来完成一个小能力点。PRP 必须解释每个引用为何必要。

## 5. 状态与权限

| 状态 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| 候选 | 调查、提问、编写 INITIAL | 修改生产代码 |
| PRP 待确认 | 只读检索、生成计划和测试策略 | 执行计划 |
| 已授权实施 | 完成当前能力点；用户默认写生产代码 | 扩展下一能力点 |
| 测试阶段 | AI 直接补本步测试并运行验证 | 借测试改变产品合同 |
| 验收阶段 | 自动验证、人工路径、解释检查、文档同步 | 把 SKIP 或计划写成通过 |
| Git 阶段 | 仅按明确授权暂存／提交／推送 | `git add .` 或带入无关改动 |

## 6. 与学习路线的关系

上下文工程负责“每一步怎样向 AI 提供正确资料”，学习路线负责“应该按什么顺序学习”。两者都不能覆盖产品方案和详细设计。当前入口始终是 M0-1，直到用户说“下一步”并完成其验收。
