| D07 | 应用协议采用固定长度帧头＋UTF-8 JSON 正文；TCP／TLS 只提供字节流，应用负责拆帧。 | Q45 |
| D08 | 帧头固定 8 字节：`magic:uint16`、`version:uint8`、`type:uint8`、`body_length:uint32`；多字节整数统一大端序。 | Q46 |
| D09 | 单帧 JSON 正文最多 64 KiB，即 65,536 字节；发送与接收双向执行。上限不含 8 字节帧头和 TLS 开销。 | Q47 |

接收顺序固定为：收齐 8 字节帧头 → 校验 magic／版本／类型／正文长度 → 在分配前拒绝超限 → 收齐正文 → 解析 UTF-8 JSON → 校验业务字段 → 调用业务处理。不得直接传输 C++ 结构体内存，也不得按对方声明的超限长度分配缓冲区。

64 KiB 检查的是序列化后的完整 JSON 字节数，包括字段名、标点、转义和元数据。恰好 65,536 字节可进入后续校验，65,537 字节必须拒绝。分页结果同时受“记录条数”和“最终序列化字节数”约束，不能截断 JSON。延期的 100 MB 文件不进入该 JSON 帧。

参考：[Qt 字节序 API](https://doc.qt.io/qt-6/qtendian.html)、[RFC 8259 JSON](https://www.rfc-editor.org/rfc/rfc8259.html)。

## 3. D10—D15：协议错误、请求关联与消息身份

| 决策 | 已确认内容 | 来源 |
| --- | --- | --- |
| D10 | 聊天文字最大 4,096 个 UTF-8 字节；超限时阻止发送、保留输入并提示，不静默截断。 | Q48 |
| D11 | 帧头、UTF-8、JSON、类型或结构等协议错误关闭当前连接；合法报文中的业务错误返回明确响应并保持连接。 | Q49 |
| D12 | 版本／协议不兼容属于永久错误：保留界面与聊天内容，暂停发送并显示原因，但停止自动重连；普通网络中断继续重连。 | Q50 |
| D13 | 所有需要响应的请求都带 `request_id`，响应原样回显；纯服务端推送不强制带 `request_id`。 | Q51 |
| D14 | 发送重试沿用同一 `local_id`；服务端按“已认证发送者＋local_id”幂等。相同键但内容或接收者冲突时拒绝。 | Q52 |
| D15 | `message_id` 是服务端持久消息身份，用于发送确认、实时推送、历史合并和去重；不单独承担断线补收进度。 | Q53、Q67—Q69 |

`request_id` 关联一次请求与响应，连接重试后是否复用由具体业务合同决定；它不等于消息身份。`local_id` 由客户端在用户首次点击发送时生成，用于解决“服务端已提交但确认丢失”的不确定性。`message_id` 在消息成功持久化后存在，是跨连接、跨设备的永久身份。客户端收到同一 `message_id` 时合并，不生成第二条气泡。

## 5. D25—D32：确认、事务、补收与游标

| 决策 | 已确认内容 | 来源 |
| --- | --- | --- |
| D25 | 发送确认超时为 5 秒；超时后气泡显示失败并允许手动重试，但不能据此断言服务端未保存。 | Q63 |
| D26 | 迟到的成功确认可把原气泡更新为“已发送”；迟到或乱序失败不能把已经成功的消息降级；重试响应合并到同一气泡。 | Q64 |
| D27 | 只有 MySQL 事务提交成功后才能向发送方确认“已发送”并向接收方推送。顺序为好友校验 → 写入 → 提交 → 确认／推送。 | Q65 |
| D28 | 提交后实时推送失败不撤销消息，也不把发送方改为失败；接收方通过补收恢复。 | Q66 |
| D29 | `message_id` 由 MySQL `BIGINT UNSIGNED AUTO_INCREMENT` 生成。允许有空洞，且并发事务提交顺序不保证等于编号顺序，因此不能作为唯一补收游标。 | Q67 |
| D30 | 每个接收账号拥有严格递增的 `delivery_seq`，作为登录／重连的补收顺序。 | Q68 |
| D31 | 客户端只确认已连续处理到的最大 `delivery_seq`；服务端持久化进度。确认丢失可导致重复下发，客户端按 `message_id` 合并。该确认不是已读回执。 | Q69 |
| D32 | 保存消息、分配接收方 `delivery_seq`、写入补收记录必须在同一 MySQL 事务中完成。 | Q70 |

三种序号的职责必须分离：

| 字段 | 作用域 | 作用 |
| --- | --- | --- |
| `message_id` | 全局消息 | 永久身份、合并、历史引用；允许空洞。 |
| `delivery_seq` | 每个接收账号 | 补收顺序和连续处理进度；不表示阅读。 |
| `conversation_seq` | 每个账号与某联系人组成的会话视图 | 历史分页、未读水位和清空水位。 |

服务端重发尚未确认的补收记录是允许的；客户端必须先按 `message_id` 幂等落入会话模型，再推进连续 `delivery_seq`。不得把“收到推送”“处理完成”“用户阅读”混成一个状态。

## 7. D37—D46：密码、重置码、限流与资料校验

| D38 | 重置码由密码学安全随机源生成 128 bit 随机量，以便人工保存的 Base32 分组形式展示，排除易混字符；输入时忽略分隔符并统一大小写。在注册 prepare 成功后只展示一次，用户确认保存后才 finalize；数据库不存明文。 | Q76、Q194、Q205 |

| D40 | 重置失败限流：15 分钟内同账号 5 次、同 IP 20 次；达到阈值后对应范围暂停 15 分钟。成功清除账号失败状态但不清除 IP 状态；响应避免泄露账号是否存在。 | Q78 |
| D41 | 重置限流状态持久化到 MySQL，服务重启后继续；数据库不可用时拒绝重置。 | Q79 |
| D42 | 登录失败限流：15 分钟内同账号 5 次、同 IP 30 次；达到阈值暂停 15 分钟。状态存 MySQL，成功只清账号状态；不影响已登录连接。 | Q80 |
| D43 | 密码为 6—128 个可见 ASCII 字符；禁止空格和其他空白、中文及非 ASCII；不强制大小写、数字或符号组合。 | Q81 |
| D44 | 账号名为 4—32 个英文字母或数字，必须以字母开头；服务端规范化为小写后判断唯一和登录，注册后不可修改。 | Q82 |
| D45 | 昵称为 1—32 个可见 Unicode 字素且不超过 128 个 UTF-8 字节，允许中文、英文、数字、普通空格、符号和 Emoji；去除首尾空格，禁止换行、制表符、控制字符及双向文本混淆字符；可重名、可修改。 | Q83、Q192、Q205 |
| D46 | 首版提供 12 个内置头像，数据库只存稳定 `avatar_id`；客户端资源映射，非法或淘汰 ID 使用默认头像；不支持上传。 | Q84 |

安全调用顺序：先做低成本格式校验与限流判定，再执行 Argon2id；成功后在事务内更新必要状态。无论账号不存在、密码错误、重置码错误还是限流触发，对未认证调用者都使用不泄露账号存在性的通用失败语义，但日志应保留内部原因。

“记住密码”与服务端密码哈希是两个边界：服务端存 Argon2id 哈希；Windows 客户端把用户明确选择保存的原始凭据交给 Credential Manager，普通配置文件只保存开关和服务器地址。

## 8. D47—D54：好友、会话、历史、清空与未读

| 决策 | 已确认内容 | 来源 |
| --- | --- | --- |
| D47 | 好友申请持久化在 MySQL，支持离线接收；保持 pending 且不自动过期，直到接收方接受／拒绝或发送方撤回。重复 pending 幂等；已是好友时报错；拒绝／撤回后可重新申请。 | Q85 |
| D48 | 双方交叉申请时在事务中自动建立好友关系，不留下第二条 pending；数据库唯一约束防止重复关系。 | Q86 |
| D49 | 删除后重新添加，双方继续原会话并可见完整旧历史；删除和重新添加写入系统事件，系统事件没有消息发送三态。 | Q87 |
| D50 | 发送时的好友关系校验与消息保存处于同一事务一致性边界；数据库锁定和提交顺序决定删除与发送谁先发生。 | Q88 |
| D51 | 每个账号视角的单聊具有严格递增 `conversation_seq`；消息和系统事件都占序号。清空历史保存该账号的 `cleared_through_seq`，新事件使用更大序号。 | Q89—Q90 |
| D52 | 历史游标分页每次最多 50 条；首次取最新页，向上滚动取更早页。数据库按序号倒序查询、客户端升序显示；游标为当前最早序号，不用 OFFSET。若 JSON 接近 64 KiB，减少本页实际条数并返回继续游标。 | Q91 |
| D53 | 服务端按账号和会话保存 `read_through_seq`。当前会话处于前台时上报已连续处理的最大序号，只能递增；用于跨设备未读。清空把读取水位推进到清空截止序号，但不向发送方产生已读回执。 | Q92 |
| D54 | 清空后双方仍是好友时保留空会话及原列表位置；已解除好友且无剩余本地内容时移出会话列表。消息区和最新预览为空，新消息或重建关系后按正常规则恢复。 | Q93、Q189、Q205 |

清空当前会话是 v1.1 新增产品需求，只作用于操作账号的会话视图并同步其设备。服务端不删除共享消息记录，不修改对方的 `cleared_through_seq`，也不通知对方。操作不可撤销，客户端必须明确写出范围并二次确认。

历史查询条件至少包含：当前账号、对端账号、`conversation_seq < cursor`（非首页）、`conversation_seq > cleared_through_seq`，并按序号倒序限制条数。逻辑表边界由 D118 固定；具体 DDL、索引名和执行计划在 M2 按该合同实现并用真实 MySQL 验证，不在产品访谈中硬编码 SQL 文本。

“有效帧”指通过基本协议解析的业务帧或心跳帧；随机垃圾、超限帧和 TLS 层流量不刷新应用心跳。重连恢复只在令牌仍有效时发生，恢复后从持久化的 `delivery_seq` 进度补收；恢复连接不能自动重发失败气泡。

## 25. 关键服务端流程

### 25.1 两阶段注册

1. 客户端生成 `registration_id`，校验表单后提交 prepare。
2. 服务端先检查格式、账号占用和持久化注册限制，再在密码池顺序生成密码与重置码的 Argon2id 哈希。
3. 服务端保存 5 分钟 pending 和 finalize token 哈希，返回一次性重置码及原始 finalize token；此时账号不能登录。
4. 用户复制并确认已保存后，客户端以同一 ID 和 token 提交 finalize。
5. 服务端事务创建账号、删除 pending 并写短期完成回执；提交后才返回注册成功，仍不创建登录会话。

### 25.2 登录

1. TCP、TLS 和 hello 依次在各自 5 秒时限内完成，进入未认证状态后才接收账号与密码。
2. 校验帧、JSON、账号和密码格式，查询账号／IP 限流；账号不存在也执行 dummy Argon2id。
3. 密码池验证哈希并判断是否需要渐进升级，结果回到数据库任务。
4. 数据库事务锁定账号并复核哈希与 `auth_version`，按规则升级哈希、清账号失败状态、撤销旧令牌并写入新令牌摘要。
5. 提交后绑定新连接，向旧连接发送 `new_login` 终止推送并关闭；新连接获得只存在进程内的原始会话令牌，然后开始补收。

### 25.3 发送消息

1. 客户端生成 `local_id`，气泡进入“发送中”，提交带 `request_id` 的请求。
2. 服务端检查认证、帧／JSON、4,096 字节文本和限流／容量。
3. 同一事务中校验好友关系、检查 `(sender, local_id)` 幂等、保存消息、取得 MySQL `message_id`、分配接收方 `delivery_seq` 和双方会话序号，然后提交。
4. 提交后回复发送确认，并尝试实时推送。推送失败不回滚。
5. 客户端按 `local_id` 合并确认，按 `message_id` 合并推送／历史；5 秒无确认显示失败，用户可手动以同一 `local_id` 重试。

### 25.4 重连补收

1. 意外断线后按退避表重新建立 TCP／TLS。
2. TLS 后完成 hello，再以 `0x16` 提交内存中的会话令牌；永久错误或令牌失效不继续自动重连。
3. 服务端校验 token 摘要、撤销／到期和 `auth_version`，先返回恢复成功，再从已持久化的连续 `delivery_seq` 之后下发补收记录。
4. 客户端逐条按 `message_id` 幂等处理，再确认最大连续进度。
5. 服务端保存进度；重复下发安全，缺口不能被跳过确认。
