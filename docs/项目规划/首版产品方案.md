# 局域网桌面聊天软件：首版产品方案

> 状态：v1.2 首版产品基线，已确认并锁定；尚未实现。
> 决策来源：产品访谈 Q1—Q38；Q89 新增“清空当前联系人会话记录”，Q93 补充其界面行为；Q39—Q271 完成 D01—D231 的详细设计确认。
> 当前规模：42 条首版产品需求。新增或改变行为仍须另行确认。

## 1. 项目定位与协作边界

- 本项目是用户的简历主项目，边学边做，技术栈围绕 C++ 扩展。
- 产品目标是在 Windows 局域网内真实使用的桌面单聊软件，断开互联网后仍可注册、登录、找回密码和聊天。
- 默认由用户编写生产代码；只有用户明确要求“帮我实现／修改／修复”时才由助手代写。
- 一次只推进一个能力点。设计、实现、验证与学习掌握分别记录；进入下一能力点须等待用户明确说“下一步”。
- Q38 锁定原 40 条需求；Q89 新增“清空当前联系人会话”，形成 v1.1 的 41 条；Q229 新增管理员注册／账号停用控制，形成 v1.2 的 42 条。Q39—Q271 的其他详细决定不得暗中增加产品功能。
- 实施起点调整为：`D:\全栈聊天软件` 从空白工程根目录按本产品合同建立；`D:\CppLearn\chathub` 只保留为工程外历史参考，不复制代码、构建配置或运行依赖到新仓库。

部署约束：服务端默认监听 `0.0.0.0:9000`，首版仅支持 IPv4；Windows 防火墙只开放“专用网络”；MySQL 不向局域网开放。TLS 证书必须包含客户端实际连接的服务器 IP。服务器不可达时保留已加载界面，但不能提交新业务或获取未加载数据。首版采用“信任局域网服务器”模型：TLS 保护传输，客户端缓存保护本机正文，但不实现端到端加密或服务端消息正文加密；拥有服务器管理员、SYSTEM 或数据库高权限的人属于受信任边界，能够读取消息正文。

## 3. 首版功能范围

### 3.1 注册、登录与密码找回

| 编号 | 已确认行为 | 来源 |
| --- | --- | --- |
| AUTH-01 | 使用自定义账号名与密码注册、登录。 | Q5 |
| AUTH-02 | 能连接服务器的局域网用户都可自助注册，不需要管理员审批或邀请码。 | Q31 |
| AUTH-03 | 服务器在注册准备阶段为待激活账号发放账号专属的唯一重置码；用户确认保存并完成注册后，正确输入该码可设置新密码。 | Q5—Q6、Q194 |
| AUTH-04 | 重置码可重复使用；重置密码后不自动作废或轮换。 | Q6 |
| AUTH-05 | 密码和重置码同时丢失时无其他找回方式，只能重新注册；新账号不继承旧账号数据。 | Q7 |
| AUTH-06 | 注册准备成功后只展示一次重置码，提供复制按钮和保存提醒；用户确认已保存后才完成注册，之后无查看入口。 | Q7、Q34、Q194 |
| AUTH-07 | “记住密码”默认不勾选；勾选后下次启动填入账号和隐藏密码，仍须点击登录。 | Q8 |
| AUTH-08 | 记住密码不得把明文密码写入普通配置文件。 | Q8 |
| AUTH-09 | 一个账号只允许一处在线；新登录成功后挤掉旧登录，旧端说明原因并返回登录界面。 | Q15 |
| AUTH-10 | 重置密码后所有现有会话失效，不自动重连，必须用新密码登录；重置码保持不变。 | Q29 |

账号规则：4—32 个英文字母或数字，必须以字母开头；统一转为小写后判断唯一与登录，注册后不可修改。密码规则：6—128 个可见 ASCII 字符，不允许空格、制表符、换行及其他空白，也不允许中文或其他非 ASCII 字符；不强制字符组合。密码下限偏弱，须依靠 Argon2id、TLS 与登录限流降低风险。

注册采用 prepare／finalize 两阶段：prepare 建立 5 分钟待激活记录并返回只展示一次的重置码，用户确认保存后才 finalize 创建账号；注册后仍须手动登录。用户必须同意服务器要求的使用须知版本，prepare 携带 `terms_version`，服务器保存接受版本和时间并拒绝版本不匹配。每 IP 15 分钟最多新建 10 个、同时最多 3 个待激活注册，24 小时最多激活 20 个账号；服务器全局最多 100 个待激活注册。重置码由 128 bit 随机量编码成排除易混字符的 26 位文本，按 `5-5-5-5-6` 展示；数据库只保存其 Argon2id 哈希。

登录、会话恢复、密码重置和退出均经过 TLS、hello 和统一帧协议。成功登录会撤销旧会话并挤下旧连接；会话令牌只存客户端进程内，恢复时不重新提交密码。密码重置递增账号认证版本并撤销全部会话；主动退出只撤销当前会话。任何操作都不允许把密码、重置码或令牌写入日志。首版不提供用户自助注销服务器账号、账号数据导出或账号名释放；这些能力后续另行设计。

### 3.2 个人资料与好友

| 编号 | 已确认行为 | 来源 |
| --- | --- | --- |
| USER-01 | 提供昵称和头像，首版内置 12 个默认头像供选择。 | Q26、Q84 |
| USER-02 | 登录账号唯一且固定；昵称用于展示，可修改且允许重名，修改不影响关系、历史或登录身份。 | Q36 |
| FRIEND-01 | 添加好友须经对方同意；接受后双方建立好友关系。 | Q9 |
| FRIEND-02 | 一方删除好友后双方解除关系，并从双方联系人列表移除。 | Q10 |
| FRIEND-03 | 解除关系后双方历史记录保留，聊天页标注“已解除好友关系”。 | Q11 |
| FRIEND-04 | 只有好友才能发送新消息；待处理申请或关系解除后不能发送，已有历史仍可查看。 | Q17 |
| FRIEND-05 | 点击联系人或会话条目进入对应联系人的单聊会话。 | 初始需求 |

昵称允许中文、英文、数字、普通空格、符号和 Emoji，长度为 1—32 个可见 Unicode 字素且不超过 128 个 UTF-8 字节；去除首尾空格后不得为空，禁止换行、制表符、控制字符和易造成双向文本混淆的字符。头像以稳定 `avatar_id` 保存，客户端资源缺失时显示默认头像。

好友申请可离线保存且不自动过期；接收方接受／拒绝或发送方撤回后结束。双方交叉申请自动建立好友关系。删除后重新添加，继续显示原会话和原历史；删除与重新添加显示系统事件，但不伪装成消息发送状态。

查找用户只支持按账号名精确查找，不提供昵称、模糊、批量、附近或推荐功能；结果只显示公开资料和双方关系状态。好友申请可附带最多 100 个 UTF-8 字节的验证消息，禁止换行、制表符和控制字符。同向待处理申请幂等，反向待处理申请自动建立好友关系。每账号最多新建 20 次／小时和 100 次／24 小时，最多保留 50 个发出待处理申请；接收方最多保留 100 个收到待处理申请。拒绝或撤回后同一对账号等待 10 分钟才能重发，删除好友后重新添加不受该冷却。

每个账号首版最多 500 个当前好友。申请列表分入站／出站并使用稳定序号分页；接受、拒绝和撤回具有明确幂等与并发顺序。删除操作携带关系版本，旧界面的迟到操作不得删除后来重新建立的关系。联系人按账号名分页，关系变化通过版本和推送合并；首次建立、重新建立和删除关系都会在双方会话中留下持久化系统事件。

### 3.3 文字聊天、历史与可靠性

| 编号 | 已确认行为 | 来源 |
| --- | --- | --- |
| MSG-01 | 首版只支持文字和 Emoji；其他消息类型后续增加。 | Q19 |
| MSG-02 | 好友离线时允许发送，服务器保存，对方下次登录或重连后自动补收。 | Q12 |
| MSG-03 | 历史由服务器保存；换电脑登录仍可查看，进入会话后分批加载。 | Q16 |
| MSG-04 | 不显示对方已读；消息只显示“发送中、已发送、发送失败”。 | Q18 |
| MSG-05 | “已发送”表示服务器事务已经提交成功，不表示对方收到或阅读。 | Q18、Q65—Q66 |
| MSG-06 | 失败时保留原消息，用户点击失败图标手动重试；不自动重复发送。 | Q21 |
| MSG-07 | 非当前会话收到消息时显示红色未读数、更新预览并置顶，不自动切换当前聊天对象。 | Q22 |
| MSG-08 | Enter 发送，Shift＋Enter 换行，同时保留“发送”按钮。 | Q32 |
| MSG-09 | 输入区提供 Emoji 面板，选择后插入当前光标位置，可与文字共同编辑发送。 | Q33 |
| MSG-10 | 当前会话处于前台时清除其未读；隐藏、最小化或查看其他会话时继续累计；不向发送方提供已读回执。 | Q35 |
| MSG-11 | 用户可清空与当前联系人的会话记录；只影响当前账号并同步其所有设备，不影响或通知对方。操作不可撤销，须二次确认；仍是好友时保留空会话，已解除好友且无剩余内容时移出会话列表，新消息或重新成为好友后可恢复显示。 | Q89—Q93、Q189 |

文字内容最多 4,096 个 UTF-8 字节，超限时阻止发送、保留输入并提示，不静默截断。`local_id` 用于同一发送者的重试幂等，`message_id` 是服务器持久身份；确认超时为 5 秒，迟到成功可把原气泡改为“已发送”，迟到失败不得把已成功消息降级。

历史每次最多返回 50 条，按会话序号使用游标加载，不使用 OFFSET；还必须满足 64 KiB 单帧上限。清空历史通过当前账号的服务端清除水位实现，不物理删除对方数据。未读进度跨设备同步，只表示本账号已处理到哪里，不构成发送方可见的已读回执。

文字发送、接收推送、补收进度、会话列表、历史、阅读进度和清空操作均已有独立协议类型。消息与系统事件分别使用永久 ID 去重；会话序号负责单聊历史，列表活动序号负责置顶，delivery 序号负责断线补收。补收采用有界窗口，重连同步完成前暂停新发送；清空使用独立操作 ID，响应丢失后的重试不能误清后来到达的消息。

未发送草稿只保存在当前 profile 的加密 SQLite 中，不上传服务器，也不在不同 profile 或不同电脑之间同步。服务器只同步已经提交成功的消息和持久系统事件。

### 3.5 管理员控制

| 编号 | 已确认行为 | 来源 |
| --- | --- | --- |
| ADMIN-01 | 本机管理员可通过 `chathub-admin.exe` 开放／关闭新账号注册，并可停用／恢复指定账号。关闭注册不影响已有账号登录；停用账号立即撤销其全部会话并禁止登录，但保留账号名、好友关系和历史，恢复后可继续使用。首版不提供 Web 管理后台、永久删除账号、内容审核或申诉流程。 | Q229 |

服务器默认最多注册 1,000 个正式账号，管理员只能在服务端配置中调低该上限。可用磁盘空间低于“5 GiB 或磁盘总容量 10%，取较大者”时，服务器自动关闭新注册和新的持久化写入，已有账号仍可登录并读取历史；恢复空间后重新检查并解除保护。保护期间返回稳定容量／存储错误并持续记录管理员告警，不自动删除历史腾出空间。

## 4. 界面方案边界

- 登录／注册区域包含登录、注册、记住密码、忘记密码和服务器设置；注册准备页一次性展示重置码，注册成功页不再展示。
- 主界面参考用户提供的微信截图，采用左侧窄导航、中间联系人／会话列表、右侧当前聊天区的三栏布局，但使用自有青绿色视觉基线、SVG 图标和设计令牌。
- 联系人列表与会话列表表示不同含义；不同联系人的消息必须严格隔离。
- 消息与会话列表采用 Qt Model/View；聊天正文可选择复制，历史向上每次加载 50 条。首版不提供全文搜索、撤回、转发、引用或单条删除。
- 主界面为简体中文浅色主题，支持高 DPI、键盘操作和基础无障碍语义。托盘右键“设置”仅保留未实现入口。
- 同一电脑通过 `--profile` 运行多个相互隔离的客户端实例，用于双客户端和单点登录测试；同一 profile 仍保持单实例。
- 首版不实现群聊、支付、公众号、音视频、图片或文件消息。
- 截图只作为布局和交互参考，不代表使用微信协议或复制微信全部功能。
- 视觉基线与交互合同已经确认，但视觉资产制作、实际实现和 UI QA 尚未完成；功能原型不能称为正式界面完成。

## 6. 已收敛的技术与交付设计

已确认的技术路线包括：Qt 6.11.1 Widgets／C++20 客户端、standalone Asio C++20 服务端、manifest vcpkg、OpenSSL 3.5 LTS、统一 TCP／TLS 长连接和应用私有 CA、8 字节大端帧头、紧凑 UTF-8 JSON、64 KiB 帧限制、独立网络／数据库／密码池、有界队列和限流、Argon2id、两阶段注册、会话令牌、完整好友与单聊协议、MySQL 8.4.11 LTS、版本化迁移、Windows shared memory、DPAPI 与 Credential Manager。登录／重置限流首版由 MySQL 持久化，Redis 只作为首版后的可替换学习扩展。

客户端使用按服务器与账号隔离的 SQLite 缓存，正文、系统事件和草稿采用 XChaCha20-Poly1305 加密，随机缓存密钥由 DPAPI CurrentUser 保护。每次启动仍须先成功在线登录才能查看缓存；每账号设置 512 MiB 软上限，只淘汰可以从服务器重新下载的数据。UI、网络和数据库分别拥有明确线程边界。

首版不实现数据库备份系统、自动更新、遥测或自动日志上传。Windows 交付采用独立 Client／Server 离线安装包、Windows 服务、严格配置和脱敏诊断；测试覆盖单元、真实 MySQL／TLS 集成、双 profile E2E、故障、安全、性能、UI 和干净环境部署。

新工程采用模块化单体和端口／适配器方向：客户端使用 Presentation Model 与单向状态流，服务端使用 Command Handler／Dispatcher、类型化事务结果和提交后事件；shared 只保存纯 C++20 合同。消息采用稳定信封和类型化载荷，协议、领域、持久化和展示模型分离。首版只实现文字载荷和未知类型占位，不提前创建空文件／语音模块。完整决定见《详细设计与技术选型.md》的 D01—D231；当前没有阻止 M0 的产品或架构待确认项。
