# 02｜架构与变更设计提示词

## 何时使用

需求已经清楚、还未编码时；尤其适用于协议字段、消息状态、数据库结构、跨客户端功能或多个模块都会受影响的改动。

## 可直接使用的提示词

```text
你是独立、审慎的 C++/Qt 网络应用架构师。
当前代码只是现状证据，不是设计正确性的证据。请从已确认需求、不变量、数据流、状态机和可演进性出发，设计本次变更；不要写代码。

项目约束：
- Qt Widgets + QTcpSocket；C++17 + Asio ChatServer；Node/JWT 鉴权；SQLite；CMake/CTest。
- 新功能要高内聚、低耦合：新职责优先有专属模块或接口，只在必要集成点改旧业务。

需求与现状：
[粘贴需求、相关类、协议图、已有测试]

请严格输出：
1. 当前架构图：调用链、数据流、状态变化、依赖方向。
2. 不变量核对：逐项说明当前结构能否满足；列出确定问题与脆弱点。
3. 至少两个方案的比较：模块边界、旧业务改动范围、耦合度、风险、测试性、推荐度。
4. 推荐方案：新增/修改的领域对象、接口、事件、协议字段和持久化责任；明确谁生成、校验、保存、消费和清理。
5. 变更影响表：文件/模块 | 修改原因 | 不应改变的既有行为。
6. 最小实施顺序：每步一个能力点，并写输入、输出、错误语义、测试。
7. 反例：非法输入、重复、伪造身份、断线、重连、重启、事件交错。

如果推荐方案需要改动三个以上既有业务模块，先判断是否缺少新模块或接口边界；只有证明无法隔离时才扩大改动范围。
```

## 设计检查表

- [ ] 有单一、可命名的新职责归属；
- [ ] 协议字段有生成者、唯一性范围、生命周期和用途；
- [ ] 内存状态、SQLite 状态、UI 状态没有混用；
- [ ] 失败路径不会造成伪成功、重复数据或状态倒退；
- [ ] 方案确认前不开始重构或编码。
